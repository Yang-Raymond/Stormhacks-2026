# LadyBug

A LeetCode-style app where, instead of solving problems, you **fix buggy code**. Practice problems come in Python, JavaScript, TypeScript, Java, C, C++ and C#; personal daily and weekly challenges are generated by Gemini. Your fix is graded against hidden test cases in a sandboxed runner.

## Services

| Service  | Path        | Port | Notes |
|----------|-------------|------|-------|
| `db`     | —           | 5432 | Postgres + TimescaleDB (same engine as Tiger Data) |
| `runner` | `runner/`   | 8000 (internal only) | Stdlib Python service that executes untrusted code |
| `server` | `server/`   | 4000 | Express 5 + TypeScript API |
| `front_end` | `front_end/` | 3000 | Next.js + Monaco; proxies `/api/*` to the server |

## Running locally

Requirements: Docker with Compose, and a [Gemini API key](https://aistudio.google.com/apikey).

```bash
cp .env.example .env
# Fill in GEMINI_API_KEY, POSTGRES_PASSWORD and SESSION_SECRET (openssl rand -hex 32)
docker compose up --build
```

Open <http://localhost:3000>. Check the API with `curl localhost:4000/api/health`.

Database migrations in [server/migrations/](server/migrations/) run automatically when the server starts, including the seeded problem set.

### Environment variables

| Variable | Required | Description |
| --- | --- | --- |
| `GEMINI_API_KEY` | yes | Problem generation for challenges, and hints |
| `GEMINI_MODEL` | | Defaults to `gemini-2.5-flash` |
| `SESSION_SECRET` | yes | At least 32 characters |
| `POSTGRES_PASSWORD` | yes | Password for the local `db` container |
| `DATABASE_URL` | | Use an external database such as Tiger Cloud instead of the local container (see below) |
| `PUBLIC_URL` | | The app's public address; used for OAuth redirects. Defaults to `http://localhost:3000` |
| `NODE_ENV` | | Set to `production` when deployed (makes session cookies `secure`) |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | | Enables "Log in with GitHub" |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | | Enables "Log in with Google" |

### OAuth

Register an OAuth app with each provider and set its callback URL to `<PUBLIC_URL>/api/auth/oauth/<provider>/callback`, for example `http://localhost:3000/api/auth/oauth/github/callback`. Login buttons only appear for providers whose credentials are set.

### Tiger Cloud

Put the service's connection string in `DATABASE_URL`, adding `uselibpqcompat=true&` before `sslmode`:

```env
DATABASE_URL=postgres://tsdbadmin:<password>@<host>:<port>/tsdb?uselibpqcompat=true&sslmode=require
```

Then `docker compose up -d server` (not `restart`, which keeps the old environment). Details in [docs/integrations.md](docs/integrations.md).

## Deploying

1. Use a Tiger Cloud `DATABASE_URL`, set `NODE_ENV=production` and set `PUBLIC_URL` to the public HTTPS address.
2. Put a reverse proxy with HTTPS in front of the front end, e.g. Caddy: `ladybug.tech { reverse_proxy localhost:3000 }`. The proxy must overwrite `X-Forwarded-For`, because rate limits rely on it.
3. Only expose ports 80/443. The API (4000) and database (5432) are already bound to localhost in [docker-compose.yml](docker-compose.yml), and the runner has no published port.
4. Update the OAuth callback URLs to the production address.

Note: the compose file runs the dev servers (`next dev`, `tsx watch`) with hot reload. For a long-lived deployment, switch them to `npm run build` + `npm start`.

## Sandbox

User code only ever runs inside the `runner` container, which has:

- no internet access (an internal-only Docker network),
- a read-only filesystem (except a size-limited `/tmp`), a non-root user and all Linux capabilities dropped,
- memory, CPU and process-count limits,
- per-run rlimits, a timeout, an empty environment, and the whole process group killed afterwards.

This is solid for a hackathon, but not hardened against determined attackers. For that, run each job under gVisor or in its own short-lived container.

## Development notes

- `server/` and `front_end/` are bind-mounted, so edits hot-reload. After changing a `package.json`, rebuild that service: `docker compose up --build server`.
- Migrations: add a new file with the next free number and never edit an applied one (they're tracked in `schema_migrations`). A file whose first line is `-- migrate:no-transaction` runs outside a transaction, which TimescaleDB continuous aggregates need.
- Generated challenge problems are only saved if the reference fix passes every test **and** the buggy code fails at least one; otherwise generation retries.
- Server tests: `cd server && node --import tsx --test tests/*.test.ts`.
